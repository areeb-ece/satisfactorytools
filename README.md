# Satisfactory Tools

**Live: [areeb-ece.github.io/satisfactorytools](https://areeb-ece.github.io/satisfactorytools/)** · made by areeb

Ten calculators and planners for [Satisfactory](https://www.satisfactorygame.com/),
in one page. Plan a whole factory for several products at once, then size every
machine, miner, generator, belt split and train for it.

It's a static site with no build step, no framework and no server. Everything is
calculated in your browser tab, and your plans are kept in this browser only.

This is an independent fan project, not affiliated with Coffee Stain Studios.

---

## Getting started

```sh
git clone https://github.com/areeb-ece/satisfactorytools.git
cd satisfactorytools
python3 -m http.server 8080      # or: npm run serve
# open http://localhost:8080
```

The page uses JavaScript modules, which browsers won't load from `file://`, so serve
the folder rather than opening `index.html` directly.

To publish it, turn on GitHub Pages for the repository (Settings → Pages → deploy
from the `main` branch, root folder). It's served at `/satisfactorytools/` next to the
portfolio, which reserves that path.

## Checks

```sh
npm test                 # the maths (node --test, no browser)
npm i --no-save playwright@1.56.1
npm run test:browser     # every tool in Chromium: no errors, no CSP violations, no network, no sideways scroll
npm run test:features    # every feature, clicked and typed the way a player would, at desktop and phone width
DESIGN_DIR=../areeb-ece.github.io/public/design npm run test:browser    # with the shared theme and sky
DESIGN_DIR=../areeb-ece.github.io/public/design npm run test:features
```

With `DESIGN_DIR`, the checks serve `/design/` from that folder and `/fonts/` from the folder
beside it (where `/design/fonts.css` finds Libre Franklin). CI (`.github/workflows/test.yml`)
runs them all on every push, offline and with the files the live portfolio serves.


### The planner

The planner is a linear programme solved in the page by a small two-phase simplex
(`js/lib/lp.js`). There's one variable per recipe (machines at 100%) and one per raw
material, and for every item, what's made plus what comes in must cover what's used plus
the targets. Byproducts are allowed to pile up and are reported as surplus. Recipe
graphs are very degenerate, so pivots are chosen against slightly nudged right-hand
sides, and the answer is read from the true ones. During development the solver was
checked against [HiGHS](https://highs.dev) on 907 plans (every item, three objectives,
standard and all recipes), and it matched every optimum.

"Fewest raw resources" counts every resource equally, water at 0.05 (extractors go
anywhere), and hand-gathered things like slugs and remains as a last resort. Converter
recipes that turn one resource into another are off until you turn them on.

Each line's output is shared between its consumers in proportion.

### The factory diagram

The planner and the splitter tool are laid out like PrereqFlow: the chart fills the
window, with a legend strip above it, zoom controls floating in the corner and a drawer
that slides in from the right with the details of a pinned card. Everything else (the
products, inputs, options, the list of lines, sources and totals) lives in a side panel
on the left, and the list of tools folds behind the **Tools** button. On a phone the
side panel stacks above the chart.

The diagram is laid out like PrereqFlow's charts. Columns run from raw materials to
products, links that span several columns run through lanes between the cards, and
cards are ordered and placed to keep links straight with few crossings
(`js/lib/flowlayout.js`). Each machine is its own card. Wherever an item's belts split
or join, a splitter/merger card stands between the machines, labelled with the exact
ratio, such as "6×64 : 16×31" for 6 plate and 16 rod constructors.

- **Hover** a card to trace what feeds it (blue) and what it feeds (amber).
- **Click** a card to pin it and open its details. For a splitter card, that's its full build.
- **Shift+click** to keep a tree highlighted.
- **Keyboard:** the chart is one Tab stop. The arrow keys move to the nearest card in that
  direction (focusing a card traces it), Enter pins it and Escape unpins.

Factories over 600 machines are drawn one card per line instead.

### Exact splits

Any ratio is split exactly, with no rounding:

1. The rates become the smallest whole-number weights in exactly the same ratio. Typed
   decimals are read exactly; planner rates are matched to 1 part in 10⁷, well beyond
   anything it displays.
2. If the weights add up to D, a tree of 2- and 3-way splitters divides the belt into
   N = 2ᵃ·3ᵇ equal parts (N ≥ D).
3. Each output takes whole subtrees that add up to its weight, and the N − D spare parts
   loop back into a merger at the input.

Every belt then carries a whole number of 1/D shares of the input.

Several input belts, of any rates, are a balancer (`balance` in `js/lib/belts.js`).
Every build it considers has the same shape:

1. The inputs are put into groups.
2. Each group's belts merge into one, and that belt is split exactly, as above, into what
   the group sends to each output. A group that feeds a single output needs no splitter.
3. Each output merges whatever reaches it.

All the inputs in one group is "merge everything, then split". Each input in a group of
its own is "split each input on its own". In between, some inputs merge and the rest
don't. The search tries every way of grouping up to six input belts, and rules of thumb
for more. For each grouping, it tries several ways of deciding which group feeds which
output. Inputs and outputs that match exactly, or add up exactly, are paired first. Then
it keeps the build with the fewest splitters and mergers. On a tie, it prefers fewer
loops, then a lighter busiest belt. It's a search, not a proof: it reports how many builds
it compared. Against the earlier two-way choice (merge everything or split each input
alone), it was never worse on 300 random cases and used fewer pieces in half of them.

**The fastest belt you can build** caps every belt in the build:
- An input over the cap is taken as several equal belts.
- An output over it gets as few belts as can carry it, packed from the pieces that
  reach it.
- A group only merges belts that fit on one.
- A loop may only add what its belt has room for. When a split needs a loop that won't
  fit, its belt is halved (or split in three) first.

Outputs are a ratio of everything coming in, so they don't have to add up to the
inputs. The planner's splitter cards use the same balancer, with each machine feeding
them as an input and Mk.6 as the cap.

`js/lib/belts.js` builds the explicit network of splitters and mergers, and the unit tests
follow every belt of it. They check that:
- each splitter divides evenly;
- each merger takes at most three belts and loses nothing;
- each output gets exactly its weight;
- no belt carries more than the cap;
- the build has exactly the pieces the search counted.

The cases include 1234:63:17 (9 splitters, 8 mergers), 999983:1, and random ratios and
belt caps.

### Saving images

Every tool has **Save image** in the title bar. As in PrereqFlow, you pick what to draw:
- With a diagram (the planner, the splitter helper): the whole diagram, the highlighted
  trees, the pinned card with everything that feeds it and everything it feeds, the part
  on screen, the build inside a pinned splitter card, or just the panels.
- Any tool: which of its panels to include (inputs, results, tables).

Then pick the rest:
- the title block and legend, rates on the belts, and tree highlights;
- PNG at 2×, 3×, 4× or 6×, scaled down if a browser can't draw a canvas that big, or SVG;
- the current theme, the dark sheet or the light one for printing.

The credit line is always drawn. `js/export.js` reads the chart's layout, and the panels'
headings, fields, stat tiles and tables, back from the page. It turns them into drawing
operations, which `js/image.js` draws to a canvas or writes out as SVG. Colours come from
the shared palette, read through a hidden element carrying the chosen theme.

The page can't fetch its own font files (`connect-src 'none'`), so SVGs name mononoki and
Libre Franklin rather than embedding them. Where those aren't installed, similar fonts
stand in.

### Game data

`js/data.js` is built from [greeny/SatisfactoryTools](https://github.com/greeny/SatisfactoryTools)'
`data/data1.0.json` (MIT), which is extracted from the game's own `Docs.json`. Recipes
haven't changed since 1.0; 1.1 and 1.2 added features, not recipe changes. To rebuild it:

```sh
npm run data                         # download the file and rebuild js/data.js
node scripts/build-data.js data.json # or from a local copy
```

No game images are used: that repository's item icons belong to Coffee Stain Studios.

A few figures aren't in the dataset and are written out in `scripts/build-data.js` and
`js/lib/` with notes. They are:
- Somersloop slots per building;
- extractor rates;
- the Space Elevator phases at the default Game Mode cost;
- nuclear waste per rod (50 per Uranium rod, 10 per Plutonium rod);
- belt and pipe speeds;
- geothermal averages;
- Freight Car capacity (32 stacks, 2,400 m³) and the 27.08 s platform transfer;
- the coupon curve.

The drone battery estimate (4 + 1 per km) is a community figure, so the tool lets you
type the real number from the Drone Port instead.

## Design

The look is shared with [the portfolio](https://areeb-ece.github.io/),
[PrereqFlow](https://areeb-ece.github.io/prereqflow/) and
[OTU Calendar](https://areeb-ece.github.io/otucalendar/): each tool is a datasheet sheet on
the night sky, with a title block closed by a heavy bar. The page loads from the portfolio:
- `/design/tokens.css`: the master palette and its themes, plus the shared type, spacing,
  control, motion and layer scales;
- `/design/ui.css`: the `sd-` components (buttons, fields, segmented controls, tables, tabs,
  callouts, tags, dialog, toast) and the gear menu and night sky;
- `/design/fonts.css`: Libre Franklin for text;
- `/design/theme.js` and `/design/ui.js`: the visitor's saved settings, the settings panel
  and the sky.

A theme picked on any of the sites applies to all of them. `css/style.css` uses only the
master's tokens and lays the tools out; mononoki (`assets/fonts/`) sets the figures, tables,
wordmark and chart cards.

When `/design/` is missing (offline), or serves a version from before the shared scales and
components, `js/theme.js` links `assets/design/` instead, a copy of the master's `tokens.css`
and `ui.css`. Refresh it when the master changes:

```sh
cp ../areeb-ece.github.io/public/design/{tokens,ui}.css assets/design/
```

The night and paper colours at the top of `css/style.css` and the light/dark button cover
the moment before that copy loads, and offline use.

## Privacy

The page's Content Security Policy includes `connect-src 'none'`: it can't make
network requests. There are no analytics. Plans and checklists are saved in
`localStorage` under `satisfactorytools.*`. A plan you share travels inside the link
itself.
